# M12.5 — Backups + Snapshot Restore: Design

**Status:** Approved for execution (autonomous M12/Phase-1 closeout run, standing user
directive 2026-07-13 — churn not a concern, prefer durable long-term solutions, pause only for
design/usage questions the directive doesn't already answer).

**Scope precondition (PLAN.md M12.5):** "Basic world backup (SQLite snapshot / per-world export)
+ restore path; minimal manual scheduling. Distinct from Phase-4 backup *automation*." This is
the dogfood-alpha gate's data-safety precondition — it must exist before real worlds accrue, not
be a fully automated/scheduled system.

## 1. What's being backed up

Shadowcat is a single server binary with **one shared SQLite database file** (`config.db`,
default `./shadowcat.db`) holding ALL worlds (multi-tenant single file — confirmed via
`SqliteRepository`, `src/server/src/data/sqlite.rs`), plus a **sibling on-disk assets directory**
(`config.assets_path()` — explicit `assets_dir` or a directory named `assets/` beside the db
file, `src/server/src/config.rs:120-130`). The pool is single-connection
(`SqlitePoolOptions::max_connections(1)`, `src/server/src/db.rs`).

**Decision: whole-server snapshot, not per-world export.** PLAN.md's line offers "SQLite
snapshot / per-world export" as alternatives. Per-world export would require dumping a
world-scoped row subset while preserving referential integrity (cross-table FKs, shared asset
references, admin/global tables) — real complexity for a "basic" gate-precondition feature, and
it does not satisfy the safety goal any better than a whole-file snapshot for a single-tenant-per-
deployment or small-multi-tenant hosting model. A whole-server snapshot is simpler, strictly
correct (nothing can be missed), and matches how the data is actually stored. Per-world granular
export/import (for e.g. sharing a world between server instances) is a distinct feature,
deferred to `docs/TODO.md` as a future enhancement — not required for the dogfood gate.

## 2. Backup mechanism

1. **Database:** SQLite's `VACUUM INTO '<path>'` — an atomic, consistency-guaranteed snapshot of
   the live database to a new file, safe to run against a database with an open connection and
   in-flight writes (SQLite guarantees the snapshot reflects a single consistent transaction
   point; no separate connection or downtime needed). This is the standard, correct way to
   snapshot a live SQLite file — copying the raw `.db` file bytes directly is NOT safe (a
   concurrent writer can leave the file mid-write, and WAL-mode databases need a checkpoint the
   raw copy won't perform).
2. **Assets:** a recursive copy of the assets directory tree into the backup output directory,
   performed **after** the `VACUUM INTO` snapshot completes. Ordering matters: asset uploads
   write the file to disk BEFORE inserting the referencing DB row
   (`src/server/src/http/assets.rs:105-202`), so any asset the DB snapshot references was already
   on disk before the snapshot was taken, and asset files are never deleted except by an explicit
   delete request — so a DB-snapshot-then-assets-copy ordering guarantees every asset the
   snapshot's rows reference is present in the assets copy.
3. **Manifest:** a `manifest.json` written last, recording: UTC-ish wall-clock timestamp (passed
   in by the caller — Rust `SystemTime` is fine here, this is server-side, not a workflow
   script), the shadowcat crate version, the source `db` path and `assets_dir` resolved by
   `Config`, and byte counts / asset-file counts for a human sanity-check on restore.

**Known limitation (documented, not solved here):** the assets-copy step is not transactionally
coupled to the DB snapshot. An asset REPLACE (not create) in flight during backup commits its DB
row before renaming its temp file into place (`src/server/src/http/assets.rs:296-312` —
[[commit-db-row-before-swapping-file]]), so a backup racing an in-flight replace could capture
updated asset metadata with the pre-replace file bytes for a few milliseconds' window. This is
an inherent property of any online (no-downtime) backup of a live mutable system and is
acceptable for a "basic" gate-precondition backup; log it to `docs/TODO.md` as a candidate for a
future stronger-consistency mode (e.g. a brief write-quiesce during backup) if it ever matters in
practice — out of scope for M12.5.

## 3. Interface: CLI, not HTTP admin endpoint

**Decision: a CLI mode on the existing `shadowcat` binary, not a new HTTP admin endpoint.**
Shadowcat's pitch is "hostable locally via a single executable" — the CLI is already the
deployment surface (`Cli::parse()` in `main.rs`), and every host capable of running the server
binary can also run it in a one-shot backup mode from cron/Task Scheduler/systemd-timer, which
directly satisfies PLAN.md's "minimal manual scheduling" without building any admin UI or new
authenticated HTTP surface. An HTTP-triggered backup is a reasonable Phase-4 automation addition
(remote-hosting convenience) but is out of scope here — YAGNI for the gate precondition.

New CLI flags on the existing flat `Cli` struct (`src/server/src/config.rs`) — no
`clap::Subcommand` restructuring; these are optional flags that, when present, run a one-shot
operation and exit BEFORE the server binds/serves, never both a backup/restore run and a live
server in the same invocation:

- `--backup-to <DIR>`: run the backup mechanism above, writing `world.db` + `assets/` +
  `manifest.json` into `<DIR>` (created if absent; **refuses to overwrite a non-empty
  `<DIR>`** unless `--force` is also passed — no silent clobbering of a prior backup). Exits 0 on
  success, prints the manifest summary, does not start the axum server.
- `--restore-from <DIR>`: given a directory previously produced by `--backup-to` (validated
  against `manifest.json`'s presence and shape — fail closed on a malformed/foreign directory),
  copies `<DIR>/world.db` to the resolved `config.db` path and `<DIR>/assets/` to the resolved
  assets directory. **Refuses to overwrite an existing non-empty destination `db`/`assets_dir`**
  unless `--force` is passed (restore is a "reset this deployment's data" operation — a human
  running it from ops tooling might reasonably re-run it, but an accidental double-invocation
  must not silently destroy in-between work without an explicit flag). Exits 0 on success; does
  NOT start the server afterward — restore and serve are always two separate invocations, so
  there is never a live connection open on a file being replaced (Windows in particular can
  fail to replace a file with an open handle; POSIX would silently orphan the old inode under a
  live connection — neither is acceptable).
- Both flags read the SAME `db`/`assets_dir` resolution as normal server startup (CLI flag >
  `SHADOWCAT_*` env > TOML > default), so `--backup-to`/`--restore-from` target exactly the
  data a subsequent normal server invocation would use — no separate backup-specific config.
- `--backup-to` and `--restore-from` are mutually exclusive with each other and with normal
  server startup; passing either short-circuits `main()` before `SqliteRepository::connect`
  opens the long-lived pool (a fresh short-lived connection is opened for the backup/restore
  operation itself, then closed).

## 4. Implementation shape

- New module `src/server/src/backup.rs`: `pub async fn create_backup(db_path: &Path, assets_dir: &Path, out_dir: &Path) -> Result<BackupManifest, BackupError>` and `pub async fn restore_backup(backup_dir: &Path, db_path: &Path, assets_dir: &Path, force: bool) -> Result<(), BackupError>`. Pure I/O + one `VACUUM INTO` query; no dependency on `AppState`/`SqliteRepository`'s full API — a fresh `SqlitePool` (or a single `sqlx::SqliteConnection`) opened directly against `db_path` is enough, since `VACUUM INTO` is a plain SQL statement.
- `BackupManifest` (serde `Serialize`/`Deserialize`): `{ shadowcat_version: String, created_at_unix_ms: u64, source_db: String, source_assets_dir: String, asset_file_count: u64, db_bytes: u64 }`.
- `main.rs` gains an early branch: if `cli.backup_to`/`cli.restore_from` is `Some`, run the corresponding `backup`/`restore` function, print a one-line human-readable summary to stdout, and `std::process::exit(0)` (or a nonzero code with the error printed to stderr on failure) — before any `SqliteRepository::connect`/`axum::serve` call.
- `Config` gains no new fields — `--backup-to`/`--restore-from`/`--force` live on `Cli` only (they're one-shot operation triggers, not persistent server configuration; they never belong in a TOML file or `SHADOWCAT_*` env var).

## 5. Testing

- Unit: `create_backup` against a small seeded SQLite file + a temp assets dir with a few files → assert `world.db` opens and round-trips a known row, `assets/` contains the same files byte-for-byte, `manifest.json` parses and its counts match.
- Unit: `restore_backup` round-trip — backup a seeded DB, restore into fresh empty target paths, assert the restored DB matches the original by content, assets match byte-for-byte.
- Unit: `restore_backup` refuses a non-empty destination without `--force`, succeeds with it.
- Unit: `restore_backup` fails closed on a directory missing/malformed `manifest.json` (not a valid backup dir).
- Integration (CLI-level, via `assert_cmd` or direct `main`-equivalent test harness if one exists in this crate — check for precedent): `--backup-to` against a running-server-seeded db produces a directory that `--restore-from` can consume.
- Cross-platform: this touches raw filesystem copy + SQLite file I/O — verify no hardcoded path separators (`std::path::Path`/`PathBuf` throughout, per project CLAUDE.md §"Portable Paths"), and that recursive directory copy has no Unix-only assumption (no `cp -r` shell-out — use `std::fs`/`tokio::fs` walks or a small vetted crate already in the dependency tree if one exists, else hand-roll a recursive `tokio::fs::read_dir` walk).

## 6. Out of scope (Phase 4 / TODO.md)

- Scheduling/automation (cron wrapper is the OPERATOR's job for v1 — "minimal manual scheduling"
  per PLAN.md means "supports being invoked manually or by an external scheduler," not "has its
  own scheduler").
- Per-world granular export/import.
- Incremental/differential backups (every backup is a full snapshot).
- Remote backup targets (S3/etc.) — local directory only; the operator's own tooling can move the
  output directory wherever it needs to go.
- An admin HTTP-triggered backup endpoint (CLI-only, see §3).
- Stronger consistency guarantees against in-flight asset REPLACE races (§2's documented
  limitation).
