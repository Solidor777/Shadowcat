# M14c-5 · Templates Merge Server-Side — Design

**Status:** Approved (brainstorm 2026-09-01). Fifth of six M14c sub-projects (M14c-1 §1). Amends
the templates skill's "the server never merges" posture and `Document.base`'s "fully opaque"
contract — where older docs disagree with this spec, this spec wins; each carries a pointer.

## 0. Why this sub-project exists

M14c-1 established the umbrella rule: *by default, everything runs on the server; the client
requests, the server answers.* Templates are the largest remaining violation: the entire 3-way
merge (`merge3`/`computePull`/`computeRevert`/`planToUpdate` in `@shadowcat/core`) runs in the
browser, and the client dispatches the result as an ordinary batched `Update`. Three concrete
defects follow:

1. **Integrity.** The merge's 3-way `base` is client-writable (`/base` under `WRITE_FIELDS`).
   The server treats `base` as opaque, so today a forged base only corrupts the forger's own
   badge. The moment any server logic consumes `base`, that forgery becomes silent data loss in
   a future merge. Server-side merging requires server-owned `base`.
2. **Authorization drift.** `TemplatesController` re-implements capability derivation
   (`canPull`/`canPush`/`#canApplyUpdate`) as an advisory mirror. The real authority must derive
   the same decisions at apply time.
3. **Consistency with the campaign.** c-1 moved formula evaluation, c-2 combat resolution, c-3
   world-config seeding, c-4 dice-reference resolution. The merge is the last gameplay-affecting
   computation the client performs on the server's behalf.

## 1. Scope

In: the three merge intents + server merge engine + `base` ownership/validation + the client
re-plumb (controller → intents, modal fed by server conflict sets) + corpus + docs/skills.

Out (unchanged by design): **stamping** stays a client-composed `Create` (it is a clone, not a
merge; the server's authority over it is the `base` derivation in T5 plus ordinary Create
validation). `syncState` stays a client-side display derivation. Compendium/cross-world push
stays out (current `findInstances` is same-world). The conflict-resolution modal's UX is
unchanged; only its data source changes.

## 2. Decisions

| # | Decision |
|---|---|
| T1 | **The server owns the merge.** A `merge` module in the server crate is the exact behavioural twin of `@shadowcat/core`'s merge computation: `structuralDiff`/`deepEqual`/`merge3Tree`/`merge3Embedded`/`merge3`, the revert algorithms (`revertBands`/`revertEmbedded`/`revertChild`), `snapshotBase`, `restampSubtree`, `placementExclusions` (token `/engine/x|y|rotation`, hardcoded as today), and `planToUpdate`'s emission rules (whole-band changes only; `/base` refresh = the template's current snapshot; the absent-vs-empty-collection `null` rule). Conflicts keep the child-wins default and the exact `Conflict` shape (`path`/`base`/`parent`/`child`/`parentKind`), including the embedded template-deletion conflict's `base: b.system` narrowing. |
| T2 | **One conformance corpus, generated from the TS implementation, run by Rust forever.** A JSON fixture of merge cases (base/parent/child/exclusions → expected merged bands + conflicts) is GENERATED by running the TS engine over the case matrix at migration time — that generation transcript is the equivalence evidence. After the corpus exists and the Rust twin passes it, the TS computation functions (`merge3`, `merge3Tree`, `takeTemplate`, `applyResolutions`, `computePull`, `computeRevert`, `planToUpdate`, and their internal helpers) are DELETED from the client: post-migration only the server executes merges, and a second live implementation is a divergence channel, not a safety net. What stays client-side: `structuralDiff`/`deepEqual` (syncState badge), `isPlacementExcluded`/`placementExclusions`, `snapshotBase`/`stampInstance`/`restampSubtree` (stamping), `findInstances`, `syncState`, and the pure types that don't cross the wire. |
| T3 | **Three intents, stateless two-call flow.** `MergePull { request_id, child_id, resolutions? }`, `MergePush { request_id, template_id, resolutions? }`, `MergeRevert { request_id, child_id }` (the `CombatRoll` reply pattern). Without `resolutions`: the server computes the plan from live documents; conflict-free results apply immediately, conflicted results answer `MergeResult` with the conflict set (per instance for push) and write nothing for those instances. With `resolutions` (the user's "theirs" paths, per instance for push): the server RECOMPUTES the plan from live documents and rejects (`MergeError::StaleResolutions`, carrying the fresh conflict set) unless every submitted path is a current conflict path. No server-side session state; interleaving edits are caught by the recompute, not by OCC on stale pre-images. Revert never conflicts. |
| T4 | **Authorization is derived server-side against the actual computed Update.** Pull/revert: requester must be GM or the child's effective owner (the server's `effective_owner` rule, not a literal `owner` read) AND hold every capability the computed Update's change paths require (the client's `#canApplyUpdate` derivation, executed against `required_cap_for_path` on the server's side). Push: GM or effective owner of the TEMPLATE plus `/embedded` write on it; then per instance — same-world, VISIBLE to the pusher (an instance the pusher cannot see is excluded, matching the client's store-scoped `findInstances`), writable per the same per-path derivation. Invisible instances are omitted from `MergeResult` entirely (existence-hiding); visible-but-not-writable ones are reported `Excluded`, never silently stale. Authorized merge writes commit under a new `WriteOrigin::TemplateMerge` (per-op capability gates waived — the handler already derived them; scope, size, engine, containment, schema and OCC checks all still run; never derivable from a wire frame), mirroring `CombatTransition`/`ConfigSeed`. |
| T5 | **`Document.base` becomes server-owned and engine-tree-validated.** (a) The server DERIVES `base`: on any `Create` it recomputes the root document's `base` from the document's own validated bands (`snapshotBase` semantics; client-supplied `base` is discarded; no `source` → `base` is `null`; embedded children never carry `base`), and merge writes set it to the template's current snapshot. (b) `/base` leaves the client-writable field set: `required_cap_for_path` maps it to no client capability (same posture as `/source`); only server origins write it. (c) `validate_engine_tree` walks `base`: shape-checks the `MergeBase`/`EmbeddedBaseChild` structure recursively and normalizes each `engine` band via the owning doc_type — the root's own, and for embedded base children the doc_type of the live embedded child correlated by `sourceId` (no live counterpart → shape-check only, no normalization: the record is historical). The "NEVER walked" comment inverts. Egress is unchanged: `OwnerOrGm` visibility, `REDACTABLE_BANDS` membership, the independent size cap. Legacy rows are only re-validated when rewritten (validation is ingest-time, as everywhere else). |
| T6 | **Wire types are Rust-owned.** `MergeConflict`, the `MergeResult`/`MergeError` payloads, and the intent shapes are Rust types with ts-rs export (the `CombatRollEntry` precedent); the client's hand-written `Conflict` type is deleted in favour of the generated one. `ConflictGroup` stays a client UI type (it adds the display `label`). |
| T7 | **The client controller becomes an intent sender.** `TemplatesController.pull/push/revert` send the intent with a fresh `request_id`; `MergeResult` with conflicts opens the existing modal (groups keyed as today); the modal's resolve re-sends the intent with `resolutions`; `StaleResolutions` re-opens the modal with the fresh conflict set. `canPull`/`canPush` stay advisory — with ONE rule change: T3's `/base` capability removal makes `canPull`'s `canEdit(child, "/base")` leg (and `#canApplyUpdate`'s coverage of the `/base` change) unsatisfiable for non-GM effective owners, so both drop the `/base` leg, mirroring the server's `TemplateMerge` exemption of the whole-band `/base` refresh. The `excluded`-instance warning moves from controller-computed to `MergeResult`-reported. `AppContext.templates`' shape is unchanged for modules. |
| T8 | **Instances are found server-side.** A repository query (`instances_of(world, template_id)`, `json_extract` on the stored `source`) replaces the client's store scan for push; the client's `findInstances` stays only for display (e.g. instance counts in chrome). |

## 3. The `merge` module (server)

`src/server/src/merge/` — beside `formula`/`dice`. Units mirror the client modules one-to-one so
a reader can diff them, in the c-1 port style:

- `tree.rs` — `structural_diff`, `deep_equal`, pointer escape/tokenize/delete/set helpers,
  `merge3_tree`, `take_template`, `same_result`, path-overlap rules. Sorted-key traversal keeps
  output order-independent (the corpus pins order).
- `embedded.rs` — `merge3_embedded` (`source.id` correlation, never index), `revert_embedded`,
  `revert_child`, `restamp_subtree`, the `EmbeddedBaseChild` record.
- `bands.rs` — `MergeBase`/`MergeBands`, `snapshot_base`, `bands_tree`/`base_from_child`
  adapters, `placement_exclusions`/`is_placement_excluded`.
- `plan.rs` — `merge3`, `compute_pull`, `compute_revert`, `plan_to_update` (whole-band emission,
  absent-vs-empty `null` rule, `/base` = template snapshot), `apply_resolutions`.
- `mod.rs` — the public surface + `MergeConflict` (ts-rs).

Rust ownership replaces `structuredClone` discipline: every cross-tree value is cloned at the
crossing point the TS comments mark (the corpus's aliasing cases pin this behaviourally).

JSON-number semantics follow the c-1 twin conventions (`js_number` formatting where values are
rendered; `deep_equal` numeric comparison matches TS `===` on f64).

## 4. The conformance corpus

`src/client/core/src/__fixtures__/merge-conformance.json` (beside the formula corpus's home
package, since the TS engine being measured lives in `@shadowcat/core`):

- **Case matrix** covering: leaf set/delete both-sides, same-result non-conflicts, ancestor/
  descendant overlaps, array wholesale wins/conflicts, placement exclusions (token), embedded
  add/remove/reorder on each side, template-deleted child (unchanged → drop; changed → conflict),
  instance-added keep, base-missing fail-safe, template-added restamp (fresh ids — the corpus
  pins STRUCTURE with ids normalized, not literal uuids), nested embedded recursion, revert's
  drop-local-additions rule, `plan_to_update` emission (changed bands only, `null` vs `[]`,
  `/base` payload), and the conflict shape for every conflict kind.
- **Generation:** a one-off script runs each case through the TS engine and captures output;
  the vitest suite asserts the TS engine reproduces the corpus (run pre-deletion as the
  migration gate), the Rust suite asserts exact equality forever after (value equality; conflict
  order pinned by the sorted traversal).
- **Deletion gate:** the TS computation functions are deleted in the same commit that lands the
  passing Rust corpus run; the vitest corpus test goes with them. `merge.test.ts`/
  `templates.test.ts` coverage of deleted functions is removed; coverage of retained functions
  (`structuralDiff`, `syncState`, `stampInstance`, …) stays.

## 5. The intents (protocol)

```text
ClientMsg::MergePull   { request_id, child_id,    resolutions: Option<Vec<String>> }
ClientMsg::MergePush   { request_id, template_id, resolutions: Option<BTreeMap<Uuid, Vec<String>>> }
ClientMsg::MergeRevert { request_id, child_id }

ServerMsg::MergeResult { request_id, outcome: MergeOutcome }
ServerMsg::MergeError  { request_id, reason: MergeErrorKind }
```

`MergeOutcome` (ts-rs):

- `Pull { child_id, status: Applied | Conflicts(Vec<MergeConflict>) }`
- `Push { template_id, instances: Vec<PushInstanceOutcome> }` where each entry is
  `{ instance_id, name, status: Applied | Conflicts(Vec<MergeConflict>) | Excluded }` —
  `name` is the pusher-visible display name for the modal's group label. An instance
  the pusher cannot see at all is OMITTED from `instances` entirely (true
  existence-hiding parity with redaction — the pusher's store never contained it, so
  the reply carries no entry, name, or count for it); `Excluded` then means exactly
  one thing — visible but not writable.
- `Revert { child_id, status: Applied }`

**Hidden-conflict rule (egress).** Every replied conflict set is filtered to the
conflict paths the REQUESTER can see in BOTH documents: a conflict whose path
overlaps a property-override subtree hidden from the requester (`gm_only` /
`owner_or_gm`, the egress traversal's prefix semantics — a descendant path names
hidden data directly, an ancestor path carries the hidden subtree in its
`parent`/`child` values) is (a) removed from the replied set and (b) auto-resolved
child-wins in the applied result (the child value already sits in the merged bands;
excluding the conflict from the set `apply_resolutions` sees achieves both). The
merge COMPUTATION and the committed write stay over the unredacted documents — the
write side is authoritative, which also fixes the legacy hidden-field-dropping
behaviour of whole-band writes computed from redacted store views. A GM sees
everything, so a GM's conflict sets are unchanged.

`MergeErrorKind`: `NotFound` (child/template missing), `NotAnInstance` (no `source`),
`Forbidden` (the owner-or-GM gate), `StaleResolutions { outcome: MergeOutcome }` (a
submitted path that WAS a conflict on this surface but no longer is — the documents
moved between the two calls), `UnknownResolution` (a submitted path that is not a
conflict on this surface at all — never was, or, for push, a wrong/invisible
instance key), plus the shared validation/IO errors. Both resolutions rejections
carry the fresh conflict set so the client re-opens the modal without a round trip.

Application: the handler computes the plan, derives authorization per T4, and commits each
authorized instance's Update under `WriteOrigin::TemplateMerge` through the one write path, so
broadcast/redaction/event-log behaviour is identical to a client-dispatched merge today.

## 6. `Document.base` ownership and validation

Per T5. Concretely:

- `data::validation::validate_engine_tree` gains the `base` walk (shape + per-doc_type engine
  normalization, embedded correlation by `sourceId`). Its "NEVER walked" comment is rewritten to
  state the new contract: `base` is server-derived, shape-validated and engine-normalized at
  ingest like every other band.
- `data::permission::required_cap_for_path` stops mapping `/base` to `WRITE_FIELDS`; the field
  doc comment on `Document.base` is rewritten (server-owned, derived at stamp and merge; the
  `MergeBase` shape is now server-defined in `merge::bands`, mirrored in generated TS).
- Create-time derivation lives in the write path's Create branch (before validation, so the
  derived `base` is what gets validated).
- `chat`/`combat` embedded actor copies are unaffected (they never carry `base`).

## 7. Client changes

- `templatesController.svelte.ts`: pull/push/revert send intents; `pending` sessions key off
  `request_id`; the modal consumes `MergeResult`; `StaleResolutions` re-opens. The two
  exclusion-warning sites read the push outcome's `Excluded` entries. `canPull`/`canPush`,
  `syncState`, `stampInstance`, `findInstances` (display) unchanged in signature.
- `Table` wires the controller's `MergeResult`/`MergeError` subscription alongside the existing
  server-message routing.
- `MergeConflictModal` renders generated `MergeConflict` (same fields); `ConflictGroup.label`
  comes from the push outcome's `name`.
- Deleted from `@shadowcat/core`: the T2 computation list. Kept: the display/stamp helpers.
  `mergeConflict.ts`'s `ConflictGroup` stays (UI type).
- ui-kit/core tests re-fixtured: controller tests drive a fake socket answering
  `MergeResult`; the modal tests are unchanged in spirit.

## 8. Tests

- Rust `merge` unit tests (sibling files, per convention) + the corpus runner.
- WS intent tests (`ws/conn/tests/`): pull clean; pull conflicted → resolutions → applied;
  stale resolutions rejected with a fresh set; unknown resolution path rejected; pull forbidden

- Client: controller intent/result round-trips; modal re-open on stale; retained-helper suites

## 10. Risks

- **Legacy `base` rows** failing re-validation on an unrelated rewrite — mitigated by
  ingest-time-only validation plus the unresolvable-doc_type fallback (shape-check only).
  A legacy stale-schema base on a DELETED template leaves the document write-locked with
  no merge rescue — but this is SYMMETRIC with the pre-existing behaviour of the live
  `engine` band under a module schema change (a v1-shaped engine likewise fails
  `validate_engine_tree` on rewrite), not a new defect class: both are the
  module-versioning question, which is out of scope here.
- **Behavioural drift in the port** — mitigated by corpus generation from the TS engine itself
  (not hand-written expectations) and by running the corpus against BOTH suites before the TS
  deletion lands.
- **Push visibility semantics** (server sees more than the client's store did) — the
  visible-to-pusher filter in T4 replicates the client's reach exactly; a GM pusher's reach is
  unchanged because a GM already sees every world document.

## 11. Decision log (post-review fold-in)

Rulings and wire changes made after the plan executed, while folding in the final full-branch
review's findings. Each supersedes the body text above where they differ.

| # | Ruling |
|---|---|
| D1 | **The merge's three inputs are viewed through the requester's access by ONE classifier; the stored `/base` is ONE canonical, full value.** Pull, revert and push build the PARENT side from `filter_properties(template, requester_access)` — the template with every property whose override the requester cannot READ removed, the same `property_overrides`/`Access::can_see` classifier egress uses (`merge_intents::visible_template`) — and the BASE side from the stored snapshot reduced by the SAME template-side hidden set through the same procedure (`permission::redact_pointers`, applied inside `merge3` at every embedded depth), so base and parent agree on what the requester may see; the CHILD side stays unredacted. A template-hidden path is additionally EXCLUDED from the parent diff (`HiddenPointers::excludes_parent`, overlap semantics — required on its own for an array ancestor carrying a hidden element, where the reduced base and parent still differ), so a value the requester cannot see never moves into the instance's content; a child-hidden path withholds its conflict from the wire while the child-wins default stands (`HiddenPointers::withholds`). The stored `/base` is NOT requester-relative: it is `snapshot_for_instance` of the FULL, unredacted template (bands plus its recorded policy, D10), written under `WriteOrigin::TemplateMerge` and derived at Create, so consecutive merges by seats with different views never rewrite each other's snapshot (the ping-pong the previous requester-relative `/base` produced). Each seat's `syncState` compares its egress view of that one snapshot with its egress view of the template. Visibility is resolved by document IDENTITY at every embedded depth through the `MergeVisibility` oracle (`RequesterView` in production, `AllVisible` for the corpus), never by array index — the live child index and the merged output index are different spaces. T1's "exact twin" framing is retired with it: the engine's contracts are stated in its own terms and pinned by the corpus. |
| D2 | **`MergeErrorKind::Unresolvable(MergeOutcome)` joins the wire.** A submitted path that IS a current conflict but whose template side cannot be applied to the current merged shape (the ancestor/descendant conflict shape: the instance replaced a container with a scalar the template edited inside) is rejected with the fresh outcome instead of panicking the connection. The pointer helpers (`set_pointer`/`delete_pointer`/`take_template`) are fallible (`PointerError`), and push folds every resolution before its first commit so the rejection precedes any write. |
| D3 | **`/base` is emitted only when it changed.** `plan_to_update` pushes the `/base` refresh through the same `push_if_changed` rule as every other band; an instance already in sync yields an update with no changes, which the handlers report `Applied` without publishing (no no-op `Event` per clean instance per resolution round). The corpus generator's engine emitted `/base` unconditionally, so four revert cases were amended by hand (`revert-bands-take-template`, `revert-no-op-emits-no-changes`, `revert-restores-locally-deleted`, `revert-nested-embedded`), recorded in the fixture's `amendments` key and the generation transcript. |
| D4 | **Push commit contract is stated, not re-shaped.** A push commits instances one by one and is not atomic across them; a commit failure mid-loop leaves earlier instances committed with their `Event`s broadcast. No accumulated-outcomes list rides the error: the fresh outcome a `StaleResolutions` carries is recomputed from live documents, in which an already-committed instance reads `Applied`, and a re-sent intent commits the remainder. Documented on `MergeErrorKind`, the push handler and the protocol page. |
| D5 | **An unreadable template is `NotFound` for pull/revert**, matching push's existence-hiding posture (never `Forbidden`, which would confirm the template exists). |
| D6 | **T8's query reads the `source_id`/`source_pack` columns**, not `json_extract` on the stored `source`: `instances_of(world, template_id)` filters `source_pack IS NULL AND source_id = ?` over `idx_documents_source`. Same result set, indexed. |
| D7 | **Client retry and timeout.** `TemplatesController` guards re-entry per child/template id while an intent awaits its reply; a resolutions rejection whose fresh outcome no longer conflicts is re-sent once as a compute-only call (bounded to one retry) instead of warning, since the rejected call wrote nothing; `WsClient.merge`'s timeout is sized per request (`MERGE_TIMEOUT_BASE_MS` + `MERGE_TIMEOUT_PER_INSTANCE_MS` per visible instance for a push). |
| D8 | **`MergeBands` is server-internal** (no ts-rs export); `MergeBase`/`EmbeddedBaseChild` reach the client as ts-rs exports through `@shadowcat/types`, and the client's `deletePointer`/`tokenize` are deleted with the engine they served. |
| D9 | **Template overrides propagate to instances, additively, on every write that carries template content.** `merge::bands::propagate_overrides` puts every mergeable-band override of the template (`recorded_overrides`: `/name`, `/engine…`, `/system…` — never a `/base…` policy) onto the instance unless the instance already holds a tier at least as strict (`Visibility::strictness`); instance-authored overrides are never removed or widened, and embedded children take their correlated (by `source.id`) template child's policy, never a positional neighbour's. Applied server-authored at Create (`derive_create_base`, which now loads the template — a same-batch Create is consulted first — and treats an other-world template as absent) and by `plan_to_update` on every pull/push/revert (a `/permissions/property_overrides` change, exempted in `update_authorized` beside `/base` because it can only narrow an audience). This closes the recipient direction: a GM's push of a `gm_only` template value lands hidden on a player-owned instance, and the `Event`'s `/system` delta, the stored document and `/base` all strip it for the owner. **The `OwnerOrGm` tier names the owner of the document it sits on**, so a template tier is re-expressed for the instance by `relate_tier`: `OwnerOrGm` stands only when the two documents share an effective owner (`repo.effective_owner_of` on both, `load_effective_owner` in the Create arm), else it becomes `GmOnly` on the instance — another owner's private value is nobody's private value there. |
| D10 | **`/base` egress is cut per recipient by the policy the snapshot itself records.** `MergeBase` and `EmbeddedBaseChild` carry `property_overrides` (`propertyOverrides` on a record): the snapshotted document's mergeable-band policy, re-expressed for the holding instance (`snapshot_for_instance`), required at ingest by `validate_engine_tree` (an absent map would read as "nothing hidden", the fail-open direction; every key must name a mergeable band and every value parse as a tier). `permission::own_overrides` — the single source `filter_properties`, `collect_hidden`/`redact_change` and the merge oracle all read — emits, beside the unconditional whole-band `OwnerOrGm` floor, one `/base{pointer}` (or `/base/embedded/<coll>/<k>{pointer}`, recursively) entry per recorded override at its recorded tier, so the instance owner receives `/base` minus exactly what the template hid, with no template lookup on the egress path and no dependence on the instance's live children (a base record whose instance child was deleted locally stays covered). Chosen over mirroring the instance's own content-band overrides onto `/base`: that carrier is positional-vs-identity mismatched for embedded records, disappears when the owner deletes a child, and would over-hide instance-authored overrides; a snapshot travelling with the policy in force over its content is the same shape `StoredCommand.snapshot` already uses for commit-time redaction. The client's `syncState` reads the stored base through `normalizeBase` (the server's `MergeBase` defaults, so a stripped snapshot key and a nulled template band compare equal) and excludes the recorded policy maps from its diff (the snapshot's is re-expressed, the template's verbatim; a policy change already shows through the views the two policies cut). `snapshotBase` records the same policy so the two reductions agree. The corpus fixture's `/base` new values gained the (empty) policy keys by hand (second `amendments` entry + transcript note). |
